# SUMMARY: vast.ai rentals — RTX 4090 hosts failing at ssh / `uv sync`

**Last updated:** 26-10-06 (first live test: blacklisting worked, destroy hung on a hidden prompt, fixed)

Julian's 4090 rentals often fail: ssh never accepts the connection, or `uv sync` exceeds the 10-min budget. H100 rentals usually work. The 4090 is meant for UTH stage 0 probes (inference only; a 4090 cannot run tPD training) — see `convos/julian/26-10-05_uth_experiments_SUMMARY.md`.

- **Cause** [assumed]: 43 of the 50 matching 4090 offers are non-datacenter hosts [verified: offer search 26-10-05], whose port mappings and routes to PyPI vary widely. The 4090 config's perf-per-dollar sort puts the cheapest of these first.
- **Billing on failure** [verified: code]: host-caused failures now destroy the instance; other failures still leave it billing (unless `--destroy_on_exit`).
- **Implemented: datacenter filter** (Julian asked for it in chat) [verified: lint/typecheck clean, `spd-vast --list_offers` with both configs]. New required `VastConfig` field `datacenter_only: bool`; when it is true, the offer query gets `datacenter=true`. When it is false, nothing is added, because `datacenter=false` would select only non-datacenter hosts. H100 and A100 configs: `false`.
- **Config now targets the 48 GB RTX 4090** (Julian's uncommitted edit 26-10-06: `min_gpu_ram: 40`, `datacenter_only: false`), because no datacenter host offers it.
- **Host blacklist implemented** (Julian asked, no auto-restart) [verified: lint/typecheck, live offer searches and a scratch-copy test 26-10-06; the auto-append inside a real failing rental is untested]. `spd/scripts/vast_blacklist.yaml` (git-tracked, shared by all configs) lists `host_id`, `date`, `reason`. Every search adds `host_id notin [...]` (an undocumented field, so results are also asserted clean). Host-caused failures (instance vanished/dead, not booted in 900 s, ssh failing after 300 s, `uv sync` timeout) raise `HostFailure`; the launcher appends the host, destroys the instance (`_destroy_instance`: `-y`, output asserted, because the CLI prompts without `-y` and exits 0 even on failure) and re-raises; it does not rent another offer (Julian: "No restarts"). Hand entries for later problems (slow HF download). `--offer_id` looks the offer up via `ask_contract_id=` and refuses blacklisted hosts. Keyed on host, not machine, because the failures are the operator's network [concluded].
- **First live test (26-10-06)** [verified]: host 124072 (48 GB 4090, Japan) never booted (DNS error resolving cloud.vast.ai); after 900 s it was blacklisted correctly, but the destroy hung on vastai's invisible confirmation prompt, which also means `--destroy_on_exit` never worked before. Fixed; the instance was destroyed by hand. Idea, not done: fail at once on a `status_msg` with "resolve host" instead of waiting 15 min.
- **Host ids shown** in the offer table, the rent/created log lines, the "instance ready" summary and `--dry_run`.
- **A100 config** `spd/scripts/vast_a100_config.yaml` (`--config a100`): A100_SXM4, ≥ 40 GB, ≤ $1/h, reliability > 0.98, no datacenter filter; 10 offers from $0.422/h on 26-10-06.
- **GPU alternatives with ≥ 40 GB** [verified: offer search 26-10-06]: 48 GB 4090 has only 6 offers on 5 hosts, none datacenter, from $0.43/h. A100 SXM4 40 GB: 12 offers from $0.42/h (server-only hardware). RTX PRO 5000 48 GB (Blackwell): 15 offers, 4 datacenter, from $0.63/h (dc $0.75/h). Recommendation [concluded]: A100 40 GB if 40 GB suffices (training peaked at ~27 GB), else RTX PRO 5000 (no config yet). Open question: why Julian needs ≥ 40 GB.
- **Open**: (a) `min_reliability` for the 4090 config (0.95 now; the A100 and H100 configs use 0.98). (b) Auto-retry on the next offer: declined for now (Julian: "No restarts"). A custom docker image is not recommended.
