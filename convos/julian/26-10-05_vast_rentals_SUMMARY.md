# SUMMARY: vast.ai rentals — failing hosts, host blacklist, GPU configs

**Last updated:** 26-10-28 (H100 shortage re-checked: no verified H100 SXM on the market; H200 NVL via `--gpu_name` recommended as substitute, not yet rented; configs for 48 GB 4090 (default), A100, H100, RTX PRO 6000; open questions (a)–(e) below)

The topic began with Julian's RTX 4090 rentals failing, and has since covered the launcher's error messages and GPU choices when H100s are scarce. Julian's 4090 rentals often fail: ssh never accepts the connection, or `uv sync` exceeds the 10-min budget. H100 rentals usually work. The 4090 was first meant for UTH stage 0 probes (inference only; a 24 GB 4090 cannot run tPD training, which peaked at ~27 GB at batch 16) — see `convos/julian/26-10-05_uth_experiments_SUMMARY.md`. It is now also the machine for the truth-writing analyses (`convos/julian/26-10-06_truth_writing_components_SUMMARY.md`).

- **Cause** [assumed]: 43 of the 50 matching 4090 offers are non-datacenter hosts [verified: offer search 26-10-05], whose port mappings and routes to PyPI vary widely. The 4090 config's perf-per-dollar sort puts the cheapest of these first.
- **Billing on failure** [verified: code]: host-caused failures now destroy the instance; other failures (ours, e.g. a non-timeout `uv sync` error) still leave it billing and print the destroy command (with `-y`), unless `--destroy_on_exit`.
- **Implemented: datacenter filter** [decided: Julian, transcribed chat in the LOG: "ok, add datacenter = true"] [verified: lint/typecheck clean, `spd-vast --list_offers` with both configs]. New required `VastConfig` field `datacenter_only: bool`; when it is true, the offer query gets `datacenter=true`. When it is false, nothing is added, because `datacenter=false` would select only non-datacenter hosts. H100 and A100 configs: `false` (agent's choice for the H100: it works and its market is thin [concluded]).
- **Default config now targets the 48 GB RTX 4090** (Julian's edit, committed in `9bc8167`: `min_gpu_ram: 40`, `datacenter_only: false`), because no datacenter host offers it.
- **Host blacklist implemented** [decided: Julian, transcribed chat: "I want the blacklist code, also show the host number for each offer and when provisioning. No restarts though. and a config for A100"] [verified: lint/typecheck, live offer searches and a scratch-copy test 26-10-06]. `spd/scripts/vast_blacklist.yaml` (git-tracked, shared by all configs) lists `host_id`, `date`, `reason`. Every search adds `host_id notin [...]` (an undocumented field, so results are also asserted clean). Host-caused failures (instance vanished/dead, not booted in 900 s, ssh failing after 300 s, `uv sync` timeout) raise `HostFailure`; the launcher appends the host, destroys the instance and re-raises; it does not rent another offer ("No restarts"). Hand entries for later problems (slow HF download); the launcher rewrites the file on append, so notes go in `reason`, not comments. `--offer_id` looks the offer up via `ask_contract_id=` and refuses blacklisted hosts. Keyed on host, not machine, because the failures are the operator's network [concluded]. ssh "Permission denied" is blacklisted too, although a broken local key would fail the same way [concluded: the first blacklisted host would reveal a broken key].
- **Destroy on blacklist** [decided: Julian, transcribed chat: "can you add that the instance get's destroyed when it gets blacklisted"]. `_destroy_instance` passes `-y` and asserts the output is the success line or a 404, because the CLI prompts without `-y` and exits 0 even on "Aborted." and 404 [verified: CLI behaviour observed 26-10-06; 404 path tested on a real destroyed instance, success/"Aborted." with a stubbed subprocess]. The success path inside a real failing rental is untested in code.
- **First live test (26-10-06)** [verified]: host 124072 (48 GB 4090, Japan) never booted (DNS error resolving cloud.vast.ai); after 900 s it was blacklisted correctly, but the destroy hung on vastai's invisible confirmation prompt, which also means `--destroy_on_exit` never worked before (FEEDBACK.md entry 26-10-06). Fixed; the instance was destroyed by hand.
- **Blacklist contents** [verified: `spd/scripts/vast_blacklist.yaml`, 26-10-21; commits `1b7e978` 26-10-06, `5a71fcb` 26-10-15, `143e35b` 26-10-20]: 7 hosts. Six are RTX 4090: 124072 and 135676 (Japan, "not running after 900s"), 256524 (California) and 33035 (Romania), both "ssh failing after 300s: … Permission denied (publickey)", 115630 (Poland, hand entry 26-10-15: "download looked to slow") and 393491 (France, 26-10-15, publickey again). One is an H100 SXM: 638511 (Germany, 26-10-20, `uv sync` over 10 min). The 26-10-15 and 26-10-20 additions are not discussed in the LOG apart from 638511's mention on 26-10-21. Two key rejections in a row on 26-10-06 looked like a possible broken local key; Julian confirmed the hosts were bad: the third rental after them accepted the same key [verified by Julian, `C: (transcribed from chat)` in the LOG, entry *publickey flag resolved: hosts were bad*]. The entries stay.
- **Host ids shown** in the offer table, the rent/created log lines, the "instance ready" summary and `--dry_run`.
- **A100 config** `spd/scripts/vast_a100_config.yaml` (`--config a100`): A100_SXM4, ≥ 40 GB, ≤ $1/h, reliability > 0.98, no datacenter filter; 10 offers from $0.422/h on 26-10-06.
- **GPU alternatives with ≥ 40 GB** [verified: offer search 26-10-06]: 48 GB 4090 has only 6 offers on 5 hosts, none datacenter, from $0.43/h. A100 SXM4 40 GB: 12 offers from $0.42/h (server-only hardware). RTX PRO 5000 48 GB (Blackwell): 15 offers, 4 datacenter, from $0.63/h (dc $0.75/h). Recommendation [concluded]: A100 40 GB if 40 GB suffices (training peaked at ~27 GB), else RTX PRO 5000 (no config yet).
- **"Offer taken" error is often wrong** [verified: reproduced 26-10-16]: vast.ai answers `no_such_ask … Instance type by id X is not available` both for an offer someone rented and for one that is unavailable. The launcher reports both as "taken". In the reproduction, offer 53867746 (host 371998, 48 GB 4090, Zhejiang) failed this way but stayed `rented: False, rentable: False` for 2 min afterwards: nobody rented it. The same create arguments rented the next offer (host 60400, Texas) at once, so our call is fine; that test instance was destroyed. The launcher already moves on to the next offer after such a failure; Julian's run had only one offer. Done: the message now reads "Offer N (host H) is not available - rented by someone else or withdrawn by its host" [decided: Julian, transcribed chat in the LOG]; no re-query, no auto-blacklist. The error does not suggest blacklisting the host, because Julian cannot keep track of which host keeps failing [decided: Julian, transcribed chat in the LOG]. To rent past such an offer: launch again, or pick another offer with `--offer_id`. No search field predicts such offers [concluded, from one example]: the offer passed `rentable=true` seconds before failing. Minutes later all GPU offers of host 371998 (3 machines) were `rentable: False`, so the whole host went down. Only a reactive filter (skip/blacklist after the failure) works.
- **H100 shortage, alternatives** (26-10-28 snapshot, offers change within minutes) [verified: offer searches, LOG entry *H100 shortage 26-10-28*]: 4 single-GPU H100 SXM offers exist, none on a verified host. The search hardcodes `verified=true` (in `run_vast.py`, not a config field), so no config edit makes `--config h100` find one. Options: (1) **H200 NVL** (Hopper, 140 GB): `spd-vast ... --config h100 --gpu_name H200_NVL`, 7 matching offers at $4.01–4.16/h (one at $6.01), reliability ≥ 0.99; same compute capability as the H100 [concluded], speed for our workload unmeasured [assumed: ≥ H100, more memory bandwidth, DLPerf 391–454 vs 345–363]. (2) An unverified H100 SXM via `--offer_id` (which skips the config filters, checking only blacklist and countries): two in Japan at $2.40/h (host 743471) pass every other filter; risk: unvetted host. The 26-10-21 snapshot (6 offers, 2 passing) is in the LOG.
- **RTX PRO 6000 config** `spd/scripts/vast_rtxpro6000_config.yaml` (`--config rtxpro6000`) [decided: Julian, transcribed chat in the LOG: "please create the config"; values are the agent's choice] [verified: `--list_offers`, 9 offers from $1.37/h on 26-10-21]: `RTX_PRO_6000_WS` (server variant via `--gpu_name RTX_PRO_6000_S`), ≥ 90 GB, ≤ $2/h, disk 100 GB, reliability > 0.98, no datacenter filter, sort perf-per-dollar.
  - **Rented 26-10-21** (by Julian, for Exp 4e) [assumed: with `--config rtxpro6000`; the instance's repo copy contained the new config, but the launch command is not recorded] [verified: `nvidia-smi` and step counters, one measurement, `convos/julian/26-10-16_faithful_targeting_LOG.md`, entry *what do the components carry: extended ablations*]: torch 2.8.0+cu128 runs on it (compute capability 12.0); power limit 420 W. One 4e all-token training runs at 1.72 it/s, 0.68× the H100's 2.53, using 30 GB; two in parallel give 1.62 it/s in total (no gain, unlike the H100's +15%), so trainings run one at a time there and inference jobs use the free memory.
