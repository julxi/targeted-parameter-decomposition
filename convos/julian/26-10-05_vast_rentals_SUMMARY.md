# SUMMARY: vast.ai rentals — RTX 4090 hosts failing at ssh / `uv sync`

**Last updated:** 26-10-06 (sync, then the publickey flag resolved: the two blacklisted hosts were bad, per Julian)

Julian's 4090 rentals often fail: ssh never accepts the connection, or `uv sync` exceeds the 10-min budget. H100 rentals usually work. The 4090 was first meant for UTH stage 0 probes (inference only; a 24 GB 4090 cannot run tPD training, which peaked at ~27 GB at batch 16) — see `convos/julian/26-10-05_uth_experiments_SUMMARY.md`. It is now also the machine for the truth-writing analyses (`convos/julian/26-10-06_truth_writing_components_SUMMARY.md`).

- **Cause** [assumed]: 43 of the 50 matching 4090 offers are non-datacenter hosts [verified: offer search 26-10-05], whose port mappings and routes to PyPI vary widely. The 4090 config's perf-per-dollar sort puts the cheapest of these first.
- **Billing on failure** [verified: code]: host-caused failures now destroy the instance; other failures (ours, e.g. a non-timeout `uv sync` error) still leave it billing and print the destroy command (with `-y`), unless `--destroy_on_exit`.
- **Implemented: datacenter filter** [decided: Julian, transcribed chat in the LOG: "ok, add datacenter = true"] [verified: lint/typecheck clean, `spd-vast --list_offers` with both configs]. New required `VastConfig` field `datacenter_only: bool`; when it is true, the offer query gets `datacenter=true`. When it is false, nothing is added, because `datacenter=false` would select only non-datacenter hosts. H100 and A100 configs: `false` (agent's choice for the H100: it works and its market is thin [concluded]).
- **Default config now targets the 48 GB RTX 4090** (Julian's edit, committed in `9bc8167`: `min_gpu_ram: 40`, `datacenter_only: false`), because no datacenter host offers it.
- **Host blacklist implemented** [decided: Julian, transcribed chat: "I want the blacklist code, also show the host number for each offer and when provisioning. No restarts though. and a config for A100"] [verified: lint/typecheck, live offer searches and a scratch-copy test 26-10-06]. `spd/scripts/vast_blacklist.yaml` (git-tracked, shared by all configs) lists `host_id`, `date`, `reason`. Every search adds `host_id notin [...]` (an undocumented field, so results are also asserted clean). Host-caused failures (instance vanished/dead, not booted in 900 s, ssh failing after 300 s, `uv sync` timeout) raise `HostFailure`; the launcher appends the host, destroys the instance and re-raises; it does not rent another offer ("No restarts"). Hand entries for later problems (slow HF download); the launcher rewrites the file on append, so notes go in `reason`, not comments. `--offer_id` looks the offer up via `ask_contract_id=` and refuses blacklisted hosts. Keyed on host, not machine, because the failures are the operator's network [concluded]. ssh "Permission denied" is blacklisted too, although a broken local key would fail the same way [concluded: the first blacklisted host would reveal a broken key].
- **Destroy on blacklist** [decided: Julian, transcribed chat: "can you add that the instance get's destroyed when it gets blacklisted"]. `_destroy_instance` passes `-y` and asserts the output is the success line or a 404, because the CLI prompts without `-y` and exits 0 even on "Aborted." and 404 [verified: CLI behaviour observed 26-10-06; 404 path tested on a real destroyed instance, success/"Aborted." with a stubbed subprocess]. The success path inside a real failing rental is untested in code.
- **First live test (26-10-06)** [verified]: host 124072 (48 GB 4090, Japan) never booted (DNS error resolving cloud.vast.ai); after 900 s it was blacklisted correctly, but the destroy hung on vastai's invisible confirmation prompt, which also means `--destroy_on_exit` never worked before (FEEDBACK.md entry 26-10-06). Fixed; the instance was destroyed by hand.
- **Blacklist contents** [verified: `vast_blacklist.yaml` as committed in `1b7e978`, 26-10-06]: 4 hosts, all RTX 4090: 124072 and 135676 (Japan, "not running after 900s"), 256524 (California) and 33035 (Romania), both "ssh failing after 300s: … Permission denied (publickey)". Two key rejections in a row looked like a possible broken local key; Julian confirmed the hosts were bad: the third rental after them accepted the same key [verified by Julian, `C: (transcribed from chat)` in the LOG, entry *publickey flag resolved: hosts were bad*]. The entries stay.
- **Host ids shown** in the offer table, the rent/created log lines, the "instance ready" summary and `--dry_run`.
- **A100 config** `spd/scripts/vast_a100_config.yaml` (`--config a100`): A100_SXM4, ≥ 40 GB, ≤ $1/h, reliability > 0.98, no datacenter filter; 10 offers from $0.422/h on 26-10-06.
- **GPU alternatives with ≥ 40 GB** [verified: offer search 26-10-06]: 48 GB 4090 has only 6 offers on 5 hosts, none datacenter, from $0.43/h. A100 SXM4 40 GB: 12 offers from $0.42/h (server-only hardware). RTX PRO 5000 48 GB (Blackwell): 15 offers, 4 datacenter, from $0.63/h (dc $0.75/h). Recommendation [concluded]: A100 40 GB if 40 GB suffices (training peaked at ~27 GB), else RTX PRO 5000 (no config yet).
- **Open**:
  - (a) Why Julian needs ≥ 40 GB (the truth-writing plan said a 24 GB 4090); unanswered in the LOG.
  - (b) `min_reliability` for the 4090 config (0.95 now; the A100 and H100 configs use 0.98).
  - (c) Auto-retry on the next offer: declined for now (Julian: "No restarts"). A custom docker image is not recommended.
  - (d) Resolved: the publickey flag (the hosts were bad, see above).
  - (e) Not done, proposed: fail at once when a booting instance's `status_msg` contains "resolve host" instead of waiting 15 min; print the boot-wait line only when the status changes (now every 10 s).
