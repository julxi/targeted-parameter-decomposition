# FEEDBACK

A list of problems with the documentation or workflow, noted by agents (or humans), each with constructive criticism on how it could have been prevented. This is how the conventions improve instead of rotting: when an agent makes a mistake that better instructions would have prevented, the mistake gets an entry here, and a periodic review turns recurring entries into new rules.

Entry format: date, what went wrong (or what friction occurred), and — where possible — a concrete suggestion: which file should say what, so the next agent doesn't hit the same problem.

- 26-10-02 — While phasing out the subpackage `CLAUDE.md` files (renamed to `REFERENCE.md`), the agent mechanically repointed every reference to the new filename, including a code docstring ("See REFERENCE.md in this directory for usage instructions") and a "details in" pointer in `docs/CODING.md`. That kept readers being sent to documents being phased out; Julian caught it. Prevention: when a document is deprecated, each pointer to it must be classified first — a pointer that describes the deprecation stays; a pointer that sends readers there as the authority (from code, or from active rules) gets removed, not renamed. Suggested addition to CLAUDE.md, near the legacy-reference rule: "Do not add or keep pointers to the legacy references in code or active docs." (Adopted 26-10-02, approved by Julian in chat.)

- 26-10-02 — In a long session that alternated between LOG `C:` comments and chat, the agent recorded chat-triggered work in LOG entries but paraphrased Julian's chat instructions instead of transcribing them verbatim with `C: (transcribed from chat)`. That left decisions made in chat (revert scripts, "don't mark it [decided]", "not too strict") without traceable ratification until Julian asked. Prevention: whenever a chat message contains a decision or instruction, transcribe it verbatim into the LOG in the same turn the work is recorded, not just a paraphrase. Purely informational questions that lead to no decision or change need no transcription (Julian, chat, 26-10-02). A one-line reminder in CLAUDE.md's `[decided]` rule could say: "Chat messages that make a decision or trigger a change get transcribed verbatim in that turn's LOG entry; purely informational questions don't." Adopted 26-10-06 (Julian, chat; transcribed in `convos/julian/26-10-06_feedback_review_LOG.md`, entry *F2, F5b, F6 adopted; F5a/F7/F8 discussed*).

- 26-10-02 — Two avoidable restarts when launching background training jobs on the vast.ai instance over ssh. (1) `HF_HUB_OFFLINE=1` made the SPD LM run crash after loading the weights: the code still makes a Hugging Face API call (`huggingface_hub.errors.OfflineModeIsEnabled` for `api/models/Qwen/Qwen2.5-7B-Instruct`), so offline mode is not usable even with the weights cached. (2) `ssh host 'pkill -f run_trials.sh; ...'` matched its own remote command line and killed the ssh session, so the rest of the command (the fix and relaunch) never ran while the old driver kept going. Prevention: use a bracket pattern (`pkill -f "run_trials[.]sh"`) or kill by PID file, and detach launched jobs with `setsid nohup ... < /dev/null &`. (3) The same session then launched runs with WandB on via a plain `ssh vastai '<cmd>'`. That is a non-login shell, which skips `/etc/profile.d/spd_env.sh`, where `spd-vast` installs the WandB key, so every run failed with "No API key configured". Launch with `ssh vastai 'bash -lc "<cmd>"'`. If remote-job management recurs, a short "launching jobs on a rented instance" note in the training-run SUMMARY or a procedure file would be the place for it. (Adopted 26-10-03 at Julian's suggestion: these rules now live in `docs/CODING.md`, section *Running jobs on a rented vast.ai GPU*.)

- 26-10-03 — `docs/PROJECT_REFERENCE.md` had picked up new information (an updated example config path, the `route_only_selected_positions` behaviour), because CLAUDE.md and `docs/CODING.md` told agents to "correct wrong content in place" in the legacy references. Julian wants them phased out, with no new information added. Fix (adopted 26-10-03, Julian's request in chat): both rules now say to record the current fact in `convos/` and mark the legacy passage with an `OUTDATED (<date>): <reason>` line that points there. - 26-10-04 — The sync found four LOG passages that later entries had reversed (checkpoint saving at step 0 / every 2000 steps; the "correct legacy references in place" rule, twice; `docs/PROJECT_REFERENCE.md` edits that were later reverted) but that carried no `OUTDATED` marker. A reader who lands on the old passage via grep takes it as current. CLAUDE.md already describes the marker, but nothing prompts the reversing agent to go back. The sync also found two facts that existed only in chat and the SUMMARY, never in the LOG (a "faster re-runs" proposal and a probe runtime). Prevention: add a sentence to CLAUDE.md's append-only rule: "When a new entry reverses or invalidates an earlier passage, insert an `OUTDATED (<date>): <reason, pointer to the new entry>` line next to that passage in the same turn." The sync orchestrator also told its sub-agents not to touch earlier LOG content at all, which was stricter than the convention, so the markers had to be added afterwards. `docs/procedures/sync.md` could state explicitly that sync agents may insert `OUTDATED` markers. 26-10-06: the sync.md part (F5b) is adopted; the CLAUDE.md same-turn sentence (F5a) is not, for now, because of the cognitive load on the agent making the change (Julian, chat; transcribed in `convos/julian/26-10-06_feedback_review_LOG.md`, entry *F5b re-adopted, F5a on the fence*).

- 26-10-05 — Before the code-control run, the agent predicted that the control's CI probe would reach ≥ 0.97 and tagged that `[concluded]`, with a plausible but untested argument: every CI network so far had hit the ceiling. The run gave 0.654, because the trained control's CI network was nearly inactive on the probed inputs, a possibility the agent had itself listed as a risk. Julian had questioned the prediction ("I have to check this"). Prevention: a prediction about an experiment not yet run is `[assumed]`, never `[concluded]`, however strong the argument; `[concluded]` is for conclusions drawn from evidence already in hand. A one-line addition to CLAUDE.md's `[concluded]` bullet could say: "Predictions about experiments not yet run are `[assumed]`." Adopted 26-10-06 (Julian, chat; transcribed in `convos/julian/26-10-06_feedback_review_LOG.md`, entry *F2, F5b, F6 adopted; F5a/F7/F8 discussed*).

- 26-10-06 — The tPD description in the overview SUMMARY and two self-contained summaries said tPD "decomposes only what a chosen target dataset uses": the paper's design intent, written as an outcome. Julian caught it: training trades target reconstruction against sparsity, so target mechanisms can stay in Δ, and our own runs measured that cost (UTH target KL 0.433). The sentence was then copied into summaries meant for outside readers. Prevention: when summarising a method from its paper, phrase objectives as aims ("is trained to", "aims to") and name the competing loss terms. Before reusing a method description in a self-contained summary, check it against the project's own runs. Dropped 26-10-06, no rule: too specific (Julian, chat; transcribed in `convos/julian/26-10-06_feedback_review_LOG.md`, entry *reader-side sentence rejected, F7 dropped; review complete*).

- 26-10-06 — In a proposal, the agent wrote "we decompose 5 matrices because the dense Δ tensors OOM'd beyond that", paraphrasing a config comment that actually says decomposing *all 28 layers × 7 projections* OOM'd and calls the 5-matrix choice "an unvalidated guess". The paraphrase turned a guess into a constraint and would have ruled out adding layers; Julian's question about the dtype exposed it. The `[assumed]` tag didn't help, because the claim looked sourced. Prevention: when a claim rests on a code comment or config comment, quote the decisive words rather than paraphrasing, especially for limits ("OOMs", "too slow", "doesn't work"). Adopted 26-10-06 in reframed form (CLAUDE.md, *Quantitative Claims*: such a claim is `[assumed]`, quote the comment) (Julian, chat; transcribed in `convos/julian/26-10-06_feedback_review_LOG.md`, entry *F5b withdrawn, F5a rejected, F8 and F10 adopted; in-LOG markers already sanctioned*).

- 26-10-06 — The agent ran `pkill -f "truth_writers[.]py extract"` and a relaunch of `truth_writers.py extract` in one Bash call. The bracket pattern doesn't match itself, but the same shell's command line also contained the plain script name from the relaunch, so pkill killed the agent's own shell (exit 144) and the relaunch never ran. `docs/CODING.md` (*Kill by a bracket pattern or PID*) covers the remote-ssh case only. Prevention: kill in a call of its own, or by PID; the bracket trick protects only a command line that names the target nowhere else. One added sentence in that CODING.md bullet would cover it. Adopted 26-10-06 (Julian, chat; transcribed in `convos/julian/26-10-06_truth_writing_components_LOG.md`, entry *pkill rule added to CODING.md*).

- 26-10-06 — `spd-vast` called `vastai destroy instance <id>` with captured output and no `-y`. vastai 1.2.0 asks for confirmation unless it gets `-y`; the prompt was invisible and the launcher hung after blacklisting a host, while the instance kept billing. `--destroy_on_exit` had the same latent bug, so it had probably never worked. The agent had added a new caller of it without checking the CLI's `--help`. The CLI also exits 0 on "Aborted." and on 404s, so `check=True` proves nothing. Prevention: before wrapping an external CLI command whose output is captured, read its `--help` for prompts, and check the output for the success message rather than trusting the exit code. Fixed in `run_vast.py`: `_vastai` closes stdin, and `_destroy_instance` passes `-y` and asserts on the output. General lesson adopted 26-10-06 in `docs/CODING.md` *Assertions and error handling* (Julian, chat; transcribed in `convos/julian/26-10-06_feedback_review_LOG.md`, entry *F5b withdrawn, F5a rejected, F8 and F10 adopted; in-LOG markers already sanctioned*).
